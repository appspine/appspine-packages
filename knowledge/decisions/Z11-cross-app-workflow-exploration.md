## 1. 這層在談什麼

appspine 每個 app 都各自具備 M2M API Key、MCP server、Metadata Schema API 三項能力。
本文件要討論的，是**外部呼叫方（n8n、AI agent 等）如何在符合資安規範的前提下，穩固良好地
橫跨多個 app 工作**。

**定名：對外介接層**。

- 這層談的**不是**業務系統之間互相呼叫（app 對 app 直接溝通）——那是不同的問題，
  這層刻意不涉及。
- 這層談的是**單一 app 如何被外部呼叫方安全、一致、可預期地串接**：每個 app 各自
  對外暴露一致的介面慣例（key 核發、scope 設計、MCP tool 對齊、metadata 可探索性等）。
- 跨 app 的組合/編排邏輯發生在**外部呼叫方**（agent）那一端，appspine 本身不做
  app 之間的橫向溝通，只保證「每個入口都是安全、一致、可發現的」。

## 2. 已定案內容

### 2.1 Metadata Schema API 的可發現性：純目錄/發現服務（control-plane）

目標是讓外部呼叫方（n8n、AI agent 等）能快速接入、一次看到所有 app 有什麼能力。這件事
背後有兩種做法，風險差很多：

- **做法一：純目錄/發現服務（control-plane，已定案採用）**——一個輕量服務，把每個 app 的
  MCP tool 清單、scope、metadata endpoint 匯總成一份總覽，外部呼叫方打這一個地方就能一次
  探索全部 app 的能力。但**實際呼叫工具時，仍直接連到各 app 自己的 MCP server，用各 app
  自己核發的 M2M key**——這個服務只負責「告訴你有什麼、去哪裡拿」，不經手任何一次真正的
  業務呼叫。這個服務掛掉，只影響「新呼叫方接入時查不到清單」，不影響任何已經在跑的整合，
  風險等級低。
- **做法二：請求代理/聚合閘道（data-plane，不採用）**——外部呼叫方只認一個入口，所有跨
  app 的工具呼叫都先打到這個中心服務再轉發。接入體驗最簡單，但這個服務會變成所有跨 app
  呼叫的必經之路，且它自己得握有能代理所有 app 的高權限憑證（或代為保管各 app 的 key）。
  這正是 001「不設中心化服務」原本要避免的風險——單點故障 + 攻擊面收斂成一個高權限節點。
  跟「符合資安規範」這個目標互相矛盾，故不採用。

### 2.2 MCP tool 命名與 scope 對齊慣例：跨 app 統一命名前綴

**已定案**：跨 app 統一 tool 命名前綴（例如 `wiki_*`、`calendar_*`），讓外部呼叫方（agent）
一眼辨識工具來源於哪個 app。

- **不需要新增任何運行中的服務**：純粹是命名慣例，靠共用套件（`@appspine/mcp-server`）在
  tool 註冊時檢查/強制前綴格式即可
- 跟現有的 scope 格式檢查（`resource:action`）是同一種機制——compile-time／註冊時檢查，
  不是 runtime 服務，零新基礎設施
- 這種「中心化」屬於共用套件層級（像現有 `@appspine/auth`、`@appspine/mcp-server`），不是
  共用執行期服務，不會撞到 001「不設中心化服務」的風險（該原則針對的是 2.1 做法二那種
  runtime 服務，不是 compile-time 共用套件）

### 2.3 Key 核發與 scope 命名慣例：不需要跨 app 統一

**已定案**：維持 001 現有的 `resource:action` 格式即可（已經一致），不額外規定「resource
名詞要跨 app 統一命名」。

理由與 tool 命名（2.2）相反：MCP tool 名稱需要統一前綴，是因為外部呼叫方會把多個 app 的
tool 攤平成同一份清單去選擇要呼叫哪個——扁平命名空間，衝突/混淆是真實風險。Scope 不是這樣
用的：每把 M2M key 都是針對單一 app 核發，設定 scope 時使用者本來就是在某一個 app 的管理
介面情境下操作，app 本身的情境已經天然消除歧義。唯一可能有影響的是 2.1 發現服務的總覽
畫面，但只要總覽畫面照 app 分區顯示（不攤平合併成一個清單），一樣不會混淆。跨 app 協調
命名的成本高，換來的實際價值低。

### 2.4 Agent 跨 app 操作的資安邊界：已由既有設計解決，不需新機制

**已定案**：不需要額外設計一層新的「跨 app 存取控管」機制。

- 每個 app 的 M2M key 都是各自獨立驗證的（001/010 既有機制），app 之間沒有共享的信任或
  session——「可觸及範圍」就是「呼叫方手上握有哪些 app 的哪些 key」的聯集，是既有機制的
  自然結果，不是需要額外設計的新邊界
- Z16（AI Agent Team app）已定案「1 專家 agent : 1 app、各自綁定一把 scope 收斂的 key」，
  代表就算某個 agent 設定被誤用或外洩，衝擊範圍天然侷限在它綁定的那一個 app，不會因為
  「這是個跨 app 平台」而放大到其他 app
- Z11 的「每個 app 各自驗證」+ Z16 的「1 agent : 1 app」疊加，已構成資安邊界

### 2.5 跨 app 操作的稽核追蹤：關聯 id 慣例（不做中心化聚合）

**已定案**：加一個「操作關聯 id」的傳遞慣例，不做中心化日誌聚合。

- 外部呼叫方（agent）呼叫任何 app 時，可附帶一個自訂 HTTP header（例如
  `X-Appspine-Workflow-Id`），值由呼叫方自己決定/產生
- 各 app 的稽核日誌記錄機制多存這一個欄位（附加、非必要欄位，不影響既有稽核紀錄結構）
- **不是中心化聚合**：日誌仍各自留在各 app 自己的資料庫裡，appspine 不新增任何服務去收集
  /查詢跨 app 日誌；事後要追一個跨 app 工作流動到了哪些 app，靠同一個關聯 id 分別查各 app
  的日誌、人工比對，不是自動化的統一查詢介面
- **可選、非強制**：沒帶這個 header，稽核照舊正常運作，只是少了關聯欄位
- **與 Z16 銜接**：Z16（AI Agent Team app）的主持人對話已有自己的 session/對話 id 設計，
  天然可以拿來當這個關聯 id 的值，專家呼叫目標 app 的 MCP 工具時把它當 header 帶過去，
  不用另外發明一套 id 機制
